# تروفيكو — نظام إدارة طلبات المبيعات

واجهة عربية RTL مرتبطة بـNestJS وPostgreSQL لإدارة رحلة الطلب من المندوب، إلى توصية الحسابات، ثم القرار النهائي للمدير، وتجهيز المخزن وتسليم السائق حتى إثبات التسليم للعميل. تشمل صلاحيات البيانات الأساسية، واعتماد الوارد، ودفتر المخزون، وسجل تدقيق الإدارة العليا.

## التشغيل المحلي

استخدم Node 24.19.0 أو إصدارًا مدعومًا وفق `engines` وPostgreSQL. الإصدارات مثبتة في lockfile.

```sh
npm ci
# انسخ .env.example واضبط حساب runtime وحساب migrations وأصل الموقع وأسرار CSRF
npm run db:migrate:deploy
npm run build
npm run admin:bootstrap
```

أمر bootstrap يقرأ كلمة المرور مخفية من terminal أو stdin آمن، ويرفض التكرار عند وجود Admin. لا seed تلقائيًا عند التشغيل. أنشئ runtime role وطبّق `backend/ops/runtime-grants.sql` بحساب المهاجرات قبل تشغيل التطبيق. كل write حساس يستخدم نفس Prisma transaction.

شغّل في terminal منفصلين:

```sh
npm run api:start
npm start
```

افتح [النظام المحلي](http://localhost:3000/login). للتطوير: `npm run api:dev` و`npm run dev`. `API_INTERNAL_URL` الافتراضي `http://127.0.0.1:4000` يُستخدم لبناء rewrite؛ عند تغييره أعد البناء.

على هذا الجهاز جُهزت PostgreSQL معزولة على 55439 داخل `.runtime/postgres`، وقواعد `sales_dev` و`sales_test` و`sales_restore`. `npm run db:local` يعيد تشغيلها دون مسحها، ويتطلب PostgreSQL Windows المثبتة أو `PG_BIN`. الملفات الخاصة مستبعدة من Git. حساب الدخول المحلي اسمه `admin`، وكلمة مروره في `.runtime/admin-access.txt`؛ انقلها لمكان آمن وغيّرها من الملف الشخصي. قاعدة العمل تبدأ بلا طلبات/عملاء تجريبيين، ولا تُستورد بيانات المرحلة الأولى تلقائيًا.

## بداية الاستخدام

1. المندوب ينشئ مسودة ويرسل الطلب إلى الحسابات. يُولد رقم الطلب وتلتقط snapshots للعميل والمنتجات.
2. الحسابات تسجل توصية بالموافقة أو عدم الموافقة مع ملاحظة؛ التوصية استشارية ولا تعتمد الطلب.
3. المدير التجاري يرى التوصية ويقرر تنفيذها، أو الاعتماد الكامل، أو الاعتماد الجزئي، أو الرفض الكامل.
4. المخزن يحجز كل الأصناف المعتمدة معًا، ثم يعين السائق ويؤكد تسليم الطلب له؛ الصرف يحدث مرة واحدة عند هذا التسليم.
5. السائق المعين يسجل التعذر أو يؤكد وصول الطلب للعميل باسم المستلم، من دون خصم المخزون مرة ثانية.
6. كل عميل مرتبط بمنطقة واحدة، ويحدد مدير النظام منطقة أو أكثر لكل مندوب؛ لا يستطيع المندوب رؤية أو طلب إلا عملاء مناطقه.
7. الحسابات تضيف العملاء والمنتجات وتحدثها أو تعطلها، ووحدة المنتجات المعتمدة هي «عبوة». أمين المخزن يسجل الوارد، ولا يزيد الرصيد حتى توافق عليه الحسابات.
8. حساب الإدارة العليا يملك كل الصلاحيات دائمًا، وينشئ الحسابات أو يعطلها، ويدير المناطق، ويعدل صلاحيات كل دور من صفحة المستخدمين، ويرى سجل تحركات كل المستخدمين. تسري تعديلات الدور فورًا على كل مستخدميه وتُسجل في سجل العمليات، بينما تبقى صلاحيات الإدارة العليا كاملة وغير قابلة للتقليل.

الواجهات المفتوحة تتحدث كل 15 ثانية عند ظهورها، ومع focus/reconnect، وبعد نجاح إجراءات المستخدم مباشرة. هذا polling وليس دفعًا لحظيًا. لا يوجد fallback إلى بيانات وهمية عند فشل الخدمة.

## الاختبارات

```sh
npm run typecheck
npm run lint
npm test
npm run test:integration
```

التكامل يتطلب قاعدة حقيقية مستقلة ينتهي اسمها `_test` و`TEST_DATABASE_URL`، ومهاجرات مطبقة وحسابات اختبار في `.runtime/test-accounts.json`. `npm run db:seed:test` يهيئ قاعدة اختبار فارغة فقط، ويرفض إعادة seed فوق البيانات. عند الحاجة لقاعدة جديدة أنشئ قاعدة `_test` مستقلة؛ لا تستعمل reset على قاعدة العمل. سكربت التكامل يشغّل API خاصًا على 4071 ويغلقه بعد الاختبار؛ اختبار إعادة الإقلاع يستخدم 4061.

لاختبارات المتصفح على Windows/Chrome:

```powershell
$env:API_INTERNAL_URL='http://127.0.0.1:4004'
npm run build
# terminal منفصل، بنفس البيئة:
$env:TEST_API_PORT='4004'
node backend/scripts/serve-test.mjs
# terminal الاختبار:
npm run test:e2e
```

Playwright يشغّل بناء Next على 3015 ولا يعيد استخدام خادم واجهة قائم. أضف أصل `http://localhost:3015` إلى `ALLOWED_ORIGINS` للاختبار فقط. ارجع `API_INTERNAL_URL` إلى 4000 وأعد البناء لتشغيل قاعدة العمل. التقرير في `playwright-report-api`، واللقطات في `test-results`.

اختبارات واجهة mock السابقة باقية عبر `test:e2e:mock` للتطوير فقط، وتتطلب `NEXT_PUBLIC_DATA_MODE=mock` وخادم dev؛ الإنتاج يتجاهل هذا الوضع. نتائجها السابقة في وثائق المرحلة الأولى، وليست دليلًا على اختبار الباك إند.

## البنية والوثائق

- `backend/src`: config/DB، auth، schemas، application dispatch، سياسات وقراءات، أوامر الطلب، master/stock، CLI وOpenAPI. Controllers رفيعة فوق خدمات التطبيق، مع Prisma raw parameterized SQL للأقفال والقيود.
- `backend/prisma`: schema مستخرجة من القاعدة وSQL migration تتضمن CHECK وpartial unique indexes. لا تستخدم db push للإنتاج.
- `src/services/http.ts`: credentials وCSRF وتحويل الأخطاء ومفاتيح العمليات في مكان واحد. `src/services/index.ts` يختار API افتراضيًا.
- `src/domain`: الأنواع وسياسات العرض؛ السيرفر يعيد فحص كل إذن وحالة وversion.
- [عقد API](API_HANDOFF.md)، [خريطة الربط](FRONTEND_API_MAPPING.md)، [النشر](DEPLOYMENT.md)، [النسخ والاستعادة](BACKUP_RESTORE.md)، [نتائج التحقق](TEST_REPORT.md)، [مطابقة التصميم](docs/UI_REFERENCE_HANDOFF.md).

## افتراضات تحتاج مراجعة العميل قبل الإنتاج

شركة ومخزن رئيسي واحدان، ودفتر المخزون هو مصدر الحقيقة. المندوب يرى طلباته، والأدوار التشغيلية ترى الطلبات المرسلة، والمسودات خاصة بصاحبها والإدارة العليا. الإلغاء متاح قبل خروج الطلب، ولا تشمل هذه النسخة المرتجعات أو تصحيح تسليم مكتمل أو الفواتير.
