# تروفيكو — إدارة طلبات المبيعات

واجهة عربية RTL مبنية بـ Next.js App Router وReact وTypeScript strict. تنفذ دورة طلب البيع ببيانات تجريبية محلية: إنشاء ومسودة، اعتماد كامل أو جزئي ورفض، حجز مخزون، تعيين سائق، صرف وخروج، محاولات تعثر وتسليم، ومتابعة الحسابات والإدارة.

## التشغيل

يتطلب Node.js 22 أو أحدث (يفضل إصدار LTS مدعوم) وnpm. الإصدارات المثبتة موجودة في `package-lock.json`، ولا توجد إصدارات prerelease.

```sh
npm ci
npm run dev
```

افتح [التجربة المحلية](http://localhost:3000). المنفذ الافتراضي 3000؛ لتغييره استخدم `npm run dev -- --port 3001` أو `npm run start -- --port 3001`.

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

لبناء الإنتاج لا تحتاج قاعدة بيانات أو NestJS أو أسرار. استخدام Node لدى مزود الاستضافة وحده لا يثبت توافق الإعداد؛ تحقق لاحقًا من دعم Next.js وأمر start والمنفذ. لم يتم نشر التطبيق.

الجلسة في `sessionStorage` لكل تبويب. بيانات التجربة في `localStorage` بمفتاح `trofico-sales-v1` و`schemaVersion: 1`. بدء التشغيل بعد hydration فقط. تسجيل الخروج يمسح الجلسة وذاكرة الاستعلامات، ولا يمسح البيانات. تغييرات التبويبات تعيد جلب البيانات باستخدام storage events. لا توجد مزامنة بين الأجهزة.

## تجربة دورة كاملة

1. ادخل كمندوب، أنشئ طلبًا لعميل وأضف أصنافًا بكميات صحيحة، ثم أرسل وأكد الإرسال. أو احفظ مسودة ناقصة.
2. بدّل إلى المدير؛ افتح الطلب من مراجعات الإدارة. اعتمد صنفًا وارفض آخر مع السبب، ثم «إنهاء المراجعة» والتأكيد. القرارات السابقة للإنهاء محلية فقط.
3. بدّل إلى المخزن؛ افحص البنود المعتمدة والعجز، ثم أكد الجاهزية والحجز. الأصناف المرفوضة ظاهرة تاريخيًا ومستبعدة من التنفيذ.
4. بدّل إلى الحركة؛ عيّن سائقًا، ثم ابدأ التوصيل. يسجل ذلك الصرف مرة واحدة. السائق يستطيع تنفيذ المسند إليه أيضًا.
5. سجّل تعذر التسليم إن أردت، ثم التسليم الكامل باسم المستلم. يبقى سجل المحاولتين دون خصم إضافي.
6. ادخل بالحسابات وراجع نفس الطلب وكمياته وسجله، بلا صلاحية اعتماد أو صرف.

## أدوات المحاكاة

التفعيل الافتراضي `NEXT_PUBLIC_DATA_MODE=mock`؛ مثال في `.env.example`. أي قيمة أخرى توقف adapter ولا تدعي وجود API حقيقي. عند بناء ربط لاحق يجب تبديل نقطة تركيب الخدمات، وإزالة الدخول التجريبي وأدواته من واجهة الإنتاج.

«أدوات العرض التجريبي» توفر فشل الطلب التالي، تعارض الإجراء التالي، فشل الحفظ التالي، جعل المخزون المتاح صفرًا، وإضافة 1000 وحدة تجريبية. لا يحدث فشل عشوائي. التأخير 350ms. إعادة الضبط تتطلب تأكيدًا وتولد 24 طلبًا، 10 عملاء، 12 منتجًا و9 حسابات، بوقت مرجعي جديد ثابت حتى إعادة الضبط التالية.

مع Web Locks تُسلسل الكتابات بين التبويبات؛ تُطبق العملية والحجز والسجل ومفتاح منع التكرار في نسخة واحدة قبل حفظها. فشل الكتابة لا يعلن النجاح. بدون Web Locks تعمل نفس المعاملة محليًا لكن لا توجد ضمانة تنافس بين تبويبات متعددة. هذا ليس بديلًا لمعاملات قاعدة البيانات على السيرفر.

## البنية والربط لاحقًا

- `src/domain`: الأنواع والسياسات والأوامر والفلاتر المشتقة. `canViewOrder` منفصلة عن `canActOnOrder`.
- `src/services/contracts.ts`: عقد الخدمات والأوامر الصريحة، دون `updateStatus` عام.
- `src/services/mock`: التخزين والجلسة والمعاملات والـseed؛ هذا هو الجزء الوحيد الذي يصل للتخزين المحلي.
- `src/features/orders`: الخطافات والنموذج الموحد والمراجعة والتفاصيل والقوائم.
- `src/features/admin`: المستخدمون والعملاء والمنتجات والمخزون وسجل العمليات.
- `src/components`: هيكل التطبيق ومكونات Button/Dialog بنمط shadcn مع Radix لإدارة التركيز والكيبورد.
- `src/messages/ar.ts`: أسماء الأدوار والحالات والأحداث ورسائل مشتركة وتنسيق القاهرة. نصوص النماذج الخاصة بالشاشات عربية داخل مكوناتها.
- `src/app/[...path]/page.tsx`: تركيب رفيع للمسارات، دون أعمال سيرفر. التفاصيل نموذج واحد لجميع الأدوار.
- `API_HANDOFF.md`: أوامر الربط والعقود والأخطاء وإبطال الـcache.

لا توجد API Routes أو Server Actions لأعمال النظام. TanStack Query يدير جلب البيانات والإبطال، وReact Hook Form وZod للنموذج. CSS وTailwind 4، والخط Noto Sans Arabic مستضاف داخل حزمة المشروع بلا طلبات خطوط خارجية.

## افتراضات تحتاج مراجعة العميل

هذه افتراضات الوثيقة التنفيذية وليست متطلبات مؤكدة من العميل:

- الاسم والهوية مؤقتان وقابلان للاستبدال. العربية RTL فقط، دون dark mode.
- المندوب يرى طلباته ومسوداته فقط؛ الإدارات والسائقون يرون جميع المرسل. المسودات خاصة بصاحبها حتى مع Admin.
- السائق ينفذ فقط المسند إليه. الحركة تستطيع تنفيذ التوصيل بنفسها. الحسابات للمتابعة فقط.
- اعتماد الصنف كله أو رفضه؛ لا تعديل للكمية، ولا انتقال للمخزن قبل حسم كل البنود والتأكيد النهائي.
- قفل بيانات الطلب بعد الإرسال؛ التصحيح بالإلغاء وإعادة الإنشاء. لا إلغاء بعد الخروج.
- المندوب يلغي قبل قرار المدير النهائي، والمدير أو Admin قبل الخروج. Admin لا يتخطى الموافقات.
- مخزن واحد وكميات صحيحة. لا صرف أو تسليم جزئي. الحجز عند تأكيد المخزن، الصرف عند الخروج، ولا خصم عند التسليم.
- تعذر التسليم يبقي الطلب قيد التوصيل ويضيف محاولة. التسليم يحتاج اسم مستلم، والصورة والتوقيع مؤجلان.
- لا أسعار أو إيرادات أو مديونية أو ضرائب أو تحصيل. أسعار العرض مغلقة وغير منفذة.
- تعدد الأدوار مدعوم، والحسابات الأولية مستقلة. تعطيل السجلات يحفظ snapshots التاريخية. لا حذف نهائي للبيانات الأساسية.
- لا تكاملات خارجية أو إشعارات أو خرائط أو GPS أو رفع ملفات أو ERP. لا إرسال طلبات دون اتصال.

## الاختبار

```sh
npm test
npx playwright install chromium
npm run test:e2e
```

يمكن استخدام Chrome المثبت إذا تعذر تشغيل حزمة Chromium على Windows:

```powershell
$env:PLAYWRIGHT_CHANNEL='chrome'
npm run test:e2e
```

لفحص بناء الإنتاج على منفذ مستقل (مع منع إعادة استخدام خادم التطوير):

```powershell
npm run build
$env:PLAYWRIGHT_CHANNEL='chrome'
$env:PLAYWRIGHT_BASE_URL='http://localhost:3001'
$env:PLAYWRIGHT_WEB_COMMAND='npm start -- --port 3001'
npm run test:e2e
```

الاختبارات في `tests/workflow.test.ts` و`tests/e2e/workflow.spec.ts` و`tests/e2e/reference-ui.spec.ts`. تقرير Playwright في `playwright-report` واللقطات في `test-results`. انظر `TEST_REPORT.md` لنتيجة التشغيل الفعلية وحدود الفحص، و[تسليم الواجهة المرجعية](docs/UI_REFERENCE_HANDOFF.md) لخريطة الشاشات وقرارات التصميم.

## حدود المرحلة

هذه محاكاة UX وليست نظامًا إنتاجيًا أو حماية أمنية. لا تستخدم بيانات عملاء حقيقية. يلزم لاحقًا مصادقة وجلسات آمنة والتحقق من الأدوار والنطاق على السيرفر، معاملات مخزون ذرية، version checking وidempotency وسجل لا يستطيع العميل تعديله. يلزم حسم مصدر المخزون والاستضافة وسياسات الرؤية والأسعار والتسليم الجزئي قبل الباك إند والنشر.
